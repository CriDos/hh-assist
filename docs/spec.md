# Техническая спецификация hh-assist

## 1. Общие сведения и назначение

**hh-assist** — Chrome-расширение (Manifest V3), предназначенное для автоматизированного решения сертификационных тестов на платформе `assessment.hh.ru` (HeadHunter).

### Ключевые возможности:
- **Теоретические тесты:** решение вопросов с одиночным (`SINGLE`) и множественным (`MULTIPLE`) выбором по API.
- **Практические тесты (Code & SQL):** решение задач по программированию и составлению SQL-запросов с полным циклом компиляции, запуском smoke-тестов и автоматическим исправлением ошибок через LLM (self-repair).
- **Принцип единой вкладки (Single Tab Workflow):** все этапы (просмотр каталога тестов, авторизация, запуск теста по редиректу, прохождение, чтение результатов и возврат в каталог) выполняются строго в одной вкладке браузера без открытия фоновых или вспомогательных окон.
- **Работа по API:** взаимодействие с тестирующей системой осуществляется через официальные эндпоинты `/shards/*` с сохранением сессионных cookie и заголовков.
- **Синтетический фингерпринтинг:** генерация консистентных цифровых отпечатков (SHA-256 хэши компонентов, `visitorId`, `xhh`, `last_id`) для предотвращения обнаружения автоматизации на этапе инициализации теста.
- **Шлюз телеметрии (Telemetry Gate):** фильтрация событий античита в реальном времени (сокрытие ухода фокуса `WINDOW_BLUR`, событий ресайза `RESIZE`, проверочных `CANARY_DETECT`) и инжекция валидных событий решения и набора кода.
- **Интерфейс Side Panel (React 19 + Zustand + TypeScript):** современная реактивная панель управления с вкладками Очереди, Каталога тестов, Лога, Инспектора диалогов LLM, Сетевого логгера и Настроек.
- **100% TypeScript:** строгая статическая типизация всей кодовой базы, нулевой рантайм-риск регрессий.

## 4. Протокол взаимодействия с HeadHunter

### 4.1. Каталог тестов и авторизация
1. **Каталог навыков:** загружается через `GET https://hh.ru/applicant/skill_verifications/methods`.
2. **SSR структура:** извлекается из `<template class="SkillsFront-InitialState">`.
3. **Парсинг:** функция `parseCatalog` извлекает элементы категорий `SKILL` и `LANG`, сопоставляет методы прохождения (Theory / Practice), уровни сложности (Beginner, Intermediate, Advanced) и статусы доступности.

### 4.2. Инициализация контеста и редирект
- Для старта теста формируется URL редиректа вида:
  `https://hh.ru/applicant/skills/redirect_to_test?skillId=...&methodId=...&category=...&last_id=...&components=...&concat_components=...&xhh=...&fingerprintjs=...`
- Сервер возвращает `302 Found`, перенаправляющий на:
  - Теория: `https://assessment.hh.ru/tests/<skillId>?contestToken=<UUID>`
  - Практика: `https://assessment.hh.ru/code/<skillId>?contestToken=<UUID>`
- `contestToken` сохраняется в состоянии `ActiveRun` для восстановления сессии в случае перезапуска Service Worker.

### 4.3. Эндпоинты теоретических тестов (`/shards/tests/`)
| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/shards/tests/get_contest_tasks` | Получение общего списка ID заданий контеста |
| `GET` | `/shards/tests/get_current_task` | Получение текущего вопроса и вариантов ответов (`204 No Content` при завершении) |
| `POST` | `/shards/tests/submit_user_answer` | Отправка выбранных ответов (`{ taskId, answerUuids: [...] }`) |
| `POST` | `/shards/tests/post_finish` | Завершение контеста, возвращает `{ redirectUri }` на страницу результата |
| `GET` | `/shards/tests/get_time_left` | Оставшееся время контеста в секундах (`timeLeftSeconds`) |
| `POST` | `/shards/tests/report_data` | Отправка батча телеметрии активности |

### 4.4. Эндпоинты практических тестов (`/shards/code/`)
| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/code/<skillId>` (SSR) | Исходные данные задачи (`AssessmentFront-InitialState` / `pageCertCode`) |
| `POST` | `/shards/code/update_code` | Автосохранение кода во время набора (`{ taskId, text: Base64, progLanguage }`) |
| `POST` | `/shards/code/post_submit_task` | Запуск тестов (`submissionType: 'check'`) или финальная сдача (`'full'`) |
| `GET` | `/shards/code/get_submit_task_result` | Опрос результатов прогона тестов (`submissionId`, `taskId`, `isSolution`) |
| `GET` | `/shards/code/get_time_left` | Оставшееся время контеста |
| `POST` | `/shards/code/report_data` | Отправка батча телеметрии набора кода |

## 5. Шлюз телеметрии и защита от детекта

### 5.1. Таблица типов событий телеметрии
| Тип | Константа | Описание | Поведение шлюза |
|---|---|---|---|
| 1 | `WINDOW_FOCUS` | Окно браузера получило фокус | Пропускается |
| 2 | `WINDOW_BLUR` | Окно потеряло фокус (переключение вкладки) | **Блокируется** (удаляется из батча) |
| 3 | `PASTE` | Вставка из буфера обмена | **Блокируется** (удаляется из батча) |
| 4 | `RESIZE` | Изменение размера окна/панели | **Блокируется** (удаляется из батча) |
| 5 | `CODE_EDITED` | Нажатия клавиш при наборе кода | **Генерируется синтетически** порциями по 10с |
| 8 | `USER_ANSWER_SELECTED` | Выбор варианта ответа в теории | **Инжектируется шлюзом** перед submit |
| 9 | `CANARY_DETECT` | Срабатывание скрытых проверок античита | **Блокируется** (удаляется из батча) |
| 10 | `HEARTBEAT` | Периодический пинг активности | **Корректируется счетчик `[N]`** |

### 5.2. Принцип работы `telemetry-gate.ts`
1. Инжектируется через `chrome.scripting.executeScript` в контекст **Main World** целевой вкладки.
2. Перехватывает нативные функции `window.fetch`, `window.XMLHttpRequest` и `navigator.sendBeacon`.
3. Анализирует тело запросов на эндпоинты `report_data`.
4. Фильтрует детекторы ухода с вкладки (`WINDOW_BLUR`, `RESIZE`, `CANARY_DETECT`).
5. Корректирует счетчик событий в `HEARTBEAT` (type 10) на число удаленных событий.
6. Если все события в батче были отфильтрованы, шлюз возвращает синтетический успешный ответ `{ status: 200 }` без отправки запроса на сервер.
7. Добавляет в очередь отправки синтетические события ответов (`answerEvent`) и набора кода (`codeEditedEvent`), переданные сервис-воркером.

## 6. Алгоритмы решения (Solvers)

### 6.1. Теоретический солвер (`theory-solver.ts`)
```text
[Старт контеста]
       │
       ▼
[GET /shards/tests/get_current_task] ──(204 No Content)──► [POST /shards/tests/post_finish] ──► [Финиш]
       │ (200 OK: TaskItem)
       ▼
[Генерация промпта buildQuestion]
       │
       ▼
[Запрос к LLM с таймаутом и ретраями] ◄──(Ошибка парсинга ответа: до 10 попыток)
       │
       ▼
[Парсинг ответа parseAnswerResponse]
       │
       ▼
[Случайная пауза «обдумывания» delays.answer]
       │
       ▼
[Отправка телеметрии type 8 через шлюз]
       │
       ▼
[POST /shards/tests/submit_user_answer]
       │
       ▼
[Случайная пауза delays.between]
       │
       └────────────────────────────────────────────────────────┐
                                                                │
                                                                ▼
                                              (Переход к следующему вопросу)
```

### 6.2. Практический солвер (`practice-solver.ts`)
```text

       │
       ▼
[Инициализация истории диалога LLM]
       │
       ▼
 ┌──► [LLM: генерация решения (полный код файла)]
 │     │
 │     ▼
 │    [stripCodeFence: очистка markdown и reasoning-тегов]
 │     │
 │     ▼
 │    [Эмуляция набора кода: 30–60с, 3 пачки, автосохранения update_code, телеметрия type 5]
 │     │
 │     ▼
 │    [POST /shards/code/post_submit_task (check)]
 │     │
 │     ▼
 │    [Long-polling: GET /shards/code/get_submit_task_result]
 │     │
```

## 7. Фоновые сервисы (Service Worker)

### 7.1. Отказоустойчивость и Keep-Alive (`keepalive.ts`)
- **Port Heartbeat:** активный периодический пинг (каждые 15 секунд) через открытый порт `hh-panel` от Side Panel гарантирует 100% бодрствование Service Worker при открытой панели.
- **Alarms Fallback:** для предотвращения засыпания Service Worker при длительных операциях регистрируется периодический `chrome.alarms` с интервалом **12 секунд**.
- При каждом шаге выполнения активного контеста состояние сериализуется в `chrome.storage.session` под ключом `hhCheckpoint`.
- При внезапной выгрузке Service Worker (idle kill браузером) на старте воркера вызывается `restoreCheckpoint()`, восстанавливающий связь с открытой вкладкой контеста по `contestToken`.

### 7.2. Менеджер очереди (`queue.ts`)
- Очередь поддерживает пакетный запуск тестов с настраиваемыми паузами между тестами (`timingConfig.betweenTests`).
- Паузы между тестами управляемы через `AbortController` (кнопка «Стоп» прерывает паузу немедленно).
- **Graceful Error Handling:** при критическом отказе LLM API (`LLM_API`) очередь автоматически переводится в режим **Паузы** (`queuePaused = true`), сохраняя оставшиеся задачи нетронутыми до устранения проблем с сетью/ключом.

## 8. Архитектура интерфейса (Side Panel)

Интерфейс боковой панели реализован на **React 19 + TypeScript + Zustand**:
- **Изоляция состояния:** 7 специализированных сторов Zustand (`useQueueStore`, `useTestsStore`, `useLogStore`, `useLlmStore`, `useNetLogStore`, `useSessionStore`, `useSettingsStore`).
- **Связь с Service Worker:** двунаправленная связь через типизированный RPC-механизм (`chrome.runtime.sendMessage`) и стриминг логов в реальном времени через `chrome.runtime.Port` (`name: 'hh-panel'`).
- **CSP Compliance:** сборка через Vite генерирует чистый статический JS/CSS бандл без инлайн-скриптов и `eval()`, полностью удовлетворяя требованиям Content Security Policy Chrome Extensions MV3.

## 9. Сборка и тестирование

### 9.1. NPM-скрипты
| Команда | Описание |
|---|---|
| `npm run build` | Компиляция TypeScript и React в директорию `dist/` через Vite |

### 9.2. Директория сборки и релизы
Вся конфигурация и скомпилированные ассеты расширения собираются в папку `dist/`:
- Для локальной установки расширения в браузере (`chrome://extensions/`) достаточно указать путь к папке `dist/`.
- Автоматическая сборка zip-пакета и публикация релиза производятся через GitHub Actions workflow при пуше тега `v*` (например, `v1.0.0`).
